# RET-02 — Discovery and Technical Proposal (filled)

## 5. Data & Problem Discovery

| Question | Response |
|---|---|
| Selected dataset and source | A public review dataset placed at `data/raw/reviews.csv`. Recommended: Women's E-Commerce Clothing Reviews (Kaggle) for a clean single-domain run, or an Amazon Reviews release when cross-category transfer needs measuring. A synthetic bootstrap sample ships with the repo so the pipeline runs on a fresh clone; it is never used for reported results. |
| What does one record represent? | One customer's written review of one product at one point in time. A single record may raise several distinct issues, which is why the issue task is multi-label rather than multi-class. |
| Proposed target / ML objective | Both, as a multi-task problem. Sentiment (3-class, derived from star rating) answers "how bad is it"; issue category (multi-label, weak-supervised) answers "what is it about". Sentiment alone reproduces the star rating the client already has. |
| Information available at inference time | Review text only, plus optional product category (echoed, not modelled). Star rating is explicitly excluded — it is a label source, and a new review may not have one. |
| Main data quality issues | Heavy positive skew; exact and near-duplicate reviews; very short/empty reviews; non-English text; no issue labels of any kind in the source data. |
| Potential leakage risks | (a) Using star rating as a feature when it defines the sentiment label — excluded by design. (b) Same product across train and test — prevented by a grouped split, asserted before training starts. (c) Threshold tuned on test — prevented by selecting on validation only. |
| Privacy / fairness / licensing | Reviewer names and profile fields dropped at ingestion. No demographic attributes used or inferred. Dataset licence must be verified before redistribution; raw data is gitignored. Performance disparity across product category and review length is a documented check, not an assumption. |

## 6. Technical Proposal

| Question | Response |
|---|---|
| ML problem formulation | Two coupled supervised text-classification tasks: 3-class single-label sentiment, and N-label multi-label issue detection, served from one request. |
| Proposed baseline | TF-IDF (1–2 grams, sublinear) + Logistic Regression; multinomial for sentiment, one-vs-rest for issues. `class_weight="balanced"` for the positive skew. Trains in seconds and is fully interpretable. |
| Main modelling approach | One shared DistilBERT encoder with two heads — softmax over sentiment, sigmoid over issues — trained jointly (CE + weighted BCE). Shared encoding because the two judgements draw on the same evidence, and it means one forward pass serves both outputs. |
| Splitting / validation | GroupShuffleSplit on `product_id`, 70/15/15. Leakage assertion (shared products, shared exact texts) must pass or training aborts. Optional: hold out one entire product category as a transfer set. |
| Primary metrics and why | Sentiment: macro-F1 (accuracy is inflated by the positive majority). Issues: per-label precision/recall/F1 plus macro and micro F1, with average precision per label since threshold choice is a business decision. Rare labels (<25 positives) reported separately, never averaged into the headline. |
| Expected inference input | `{"text": "<raw review>", "category": "<optional>"}` |
| Expected inference output | Sentiment label + confidence, ranked issue list above threshold, `low_confidence` boolean with human-readable reasons, word count, truncation flag, model version, timestamp. |
| Main technical risks / assumptions | The issue labels are weak-supervised and unvalidated until the hand-checked sample is done — this is the dominant risk. Assumes English text. Assumes the taxonomy fits the chosen dataset's domain. Assumes rating-derived sentiment approximates written sentiment, which fails for mixed reviews ("great product, awful delivery, 3 stars"). |

## 11. Questions You Must Resolve

**1. Sentiment, issue category, or both?**
Both. Sentiment alone adds nothing to the star rating the client already sees; issue category alone can't distinguish "delivery was fast" from "delivery was a disaster". Together they produce the actionable statement the brief asks for: *"27% of negative reviews on this product are about delivery."*

**2. Do the labels genuinely represent the task?**
Sentiment labels: partially. Star ratings approximate written sentiment but break on mixed reviews. Issue labels: unknown until validated — they are generated by a keyword lexicon, and the hand-checked agreement rate described in `labeling.md` is the number that decides this. This is stated as an open risk rather than papered over.

**3. Reviews mentioning multiple issues?**
Handled natively — the issue head is multi-label (independent sigmoids), so a review can return `delivery` and `packaging` together with separate confidences. `mean_labels_true` vs `mean_labels_pred` in the evaluation report checks whether the model reproduces the real multi-label rate rather than collapsing to one label per review.

**4. Rare categories?**
Reported per-label with support counts, never hidden inside a macro average. Labels with fewer than 25 test positives are marked `rare: true` and excluded from `macro_f1_excluding_rare`. Rare labels get positive weighting during transformer training so they aren't optimised away, and average precision is reported since a single threshold suits them badly.

**5. Very short or unclear reviews?**
The system abstains. Under three words, or below the sentiment confidence threshold, or with no issue clearing the threshold → `low_confidence: true` plus a plain-language reason, and the frontend routes it to the human review queue. Empty input returns `sentiment: "unknown"`, not a guess. Nothing crashes, and nothing is invented.

**6. Transfer to another category or language?**
Category: measurably worse, and the repo provides `holdout_category()` to put a number on it rather than speculating. Domain vocabulary shifts (`fit` is meaningless for electronics) and the lexicon that generated the labels is itself domain-bound. Language: it will not transfer. Training is English-only, the language check is a crude script heuristic, and non-English input is flagged rather than scored. A multilingual encoder plus a translated or natively-labelled evaluation set would be the honest next step, not an assumption that it "probably works".
